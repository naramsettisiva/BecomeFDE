Git Field Guide

Git from a macOS terminal, for someone who has never used one. 25 minutes of setup, once. After that it's four commands a day — and a panic section for the evening one of them doesn't work.

Part 0The mental model

Almost every beginner git problem traces back to not having this picture. Five minutes here saves an hour later. Your work lives in four places, and git moves it between them.

The two questions everyone asks in week one "I committed — why isn't it on GitHub?" Because commit and push are separate. Commit saves locally; push publishes.
"I edited a file — why wasn't it committed?" Because you didn't git add it. Git only commits what you staged.

That's the whole model. Everything below is mechanics.

Part 1One-time setup · 25 minutes

The repo ships a script that walks all of this interactively and checks its own work. Run it first; the manual steps below are here so you understand what it did. 

make git-setup     # or: bash scripts/git_setup.sh

1 · Install git and know which one you have

brew install git

# open a NEW terminal, then:
which git
#  want: /opt/homebrew/bin/git   (Apple Silicon)
#    or: /usr/local/bin/git      (Intel)
#   NOT: /usr/bin/git            ← Apple's older build

If you get /usr/bin/git, Homebrew isn't first on your PATH: echo 'eval "$(/opt/homebrew/bin/brew shellenv)"' >> ~/.zprofile then exec zsh -l. Apple's git works fine for this course — this is tidiness.

2 · Tell git who you are

git config --global user.name  "Siva Naramsetti"
git config --global user.email "your@email.com"

Use the same email as your GitHub account, or GitHub's private no-reply address (Settings → Emails). If they don't match, commits show as an unattached grey avatar instead of linking to your profile — which matters when the commit history is the portfolio.

3 · Set your editor before vim ambushes you

Do this one now Run git commit without -m and a fresh Mac opens vim, which does not tell you how to leave. If it catches you first: press Esc, then type :wq and Return. Write that on a sticky note regardless. 
# nano — simple, shows its shortcuts at the bottom. Recommended.
git config --global core.editor "nano"

# or VS Code — --wait is essential, without it git thinks you finished instantly
git config --global core.editor "code --wait"

4 · Settings that prevent specific problems

git config --global init.defaultBranch main   # GitHub expects 'main'
git config --global pull.rebase true          # linear history — it's a portfolio
git config --global push.default simple
git config --global color.ui auto
git config --global credential.helper osxkeychain

5 · SSH key — how your Mac proves it's you

SSH keyHTTPS + token
Setup8 min, once3 min
Daily usesilentoccasional re-prompt
Expirynever30–90 days, then it breaks and you've forgotten why

Use SSH. Five extra minutes today avoids a confusing outage in October.

ssh-keygen -t ed25519 -C "your@email.com"
#   file location  → Return (accept default)
#   passphrase     → type one, or Return twice for none

eval "$(ssh-agent -s)"

# UseKeychain is macOS-only — this exact config won't work on Linux
cat >> ~/.ssh/config <<'EOF'

Host github.com
  AddKeysToAgent yes
  UseKeychain yes
  IdentityFile ~/.ssh/id_ed25519
EOF

ssh-add --apple-use-keychain ~/.ssh/id_ed25519
pbcopy < ~/.ssh/id_ed25519.pub    # PUBLIC key → clipboard. Note the .pub

Then GitHub → avatar → Settings → SSH and GPG keys → New SSH key. Paste. Add. Test with ssh -T git@github.com:

"…but GitHub does not provide shell access" is SUCCESS It confuses everyone the first time. GitHub is saying "I know who you are, but you can't get a terminal here" — which is correct and expected. If you see Hi <username>! You've successfully authenticated, you're done.

6 · Create the GitHub repo — and leave it empty

Do NOT tick "Add a README", ".gitignore", or "license" You already have those files locally. If GitHub creates its own, the two histories share no ancestor and your first push fails with fatal: refusing to merge unrelated histories — a genuinely baffling error for a first push. An empty repo avoids it entirely.

7 · Connect and push

cd ~/path/to/fde-trainer-bootcamp

git remote add origin git@github.com:<username>/fde-trainer-bootcamp.git
git remote -v                 # should list origin twice

make git-check                # is .env tracked? anything oversized?
git add -A
git commit -m "Day 0: bootcamp scaffold and AWS lane"
git push -u origin main       # -u only on the FIRST push

Wrong URL? Fix it with git remote set-url origin … — don't add a second remote.

Part 2The daily loop

This is 95% of what you will ever do. Four commands, or one.

End of every lab day

git status                      # what changed. READ IT.
git add -A                      # stage everything
git commit -m "Day 07: agent loop from scratch, five failure modes"
git push

Or, which also lints and runs the tests first:

make ship M="Day 07: agent loop from scratch, five failure modes"

Commit messages that are worth something

Your history is a portfolio artifact — a hiring manager scrolling it sees four weeks of daily work. If a message could apply to any day, it isn't doing its job.

BadGood
updateDay 07: agent loop from scratch, five failure modes
fixesDay 08: fix synthesis bucket — query decomposition, 0.41 → 0.87
wipDay 14: hybrid retrieval ablation on 200-doc corpus
stuffDay 18: red-team report, 50 attacks, indirect injection confirmed
Commit daily, not weekly 24 commits on 24 consecutive working days tells a story that one bulk upload does not. The cadence is the evidence.

Part 3Reading what git tells you

git status — three sections, three states

On branch main
Your branch is ahead of 'origin/main' by 2 commits.   ← 2 unpushed commits

Changes not staged for commit:                        ← edited, NOT staged
        modified:   labs/DAY_07.md

Untracked files:                                      ← new, git has never seen these
        labs/day07/agent.py

Staged (going in the next commit), not staged (edited but not going in), untracked (brand new). git add -A moves the bottom two into the first.

After a commit, and after a push

[main 3f2a1b8] Day 07: agent loop from scratch
 4 files changed, 312 insertions(+), 8 deletions(-)
        ↑ the permanent ID. You can always get back to this exact state.

To github.com:siva/fde-trainer-bootcamp.git
   9c1d4e2..3f2a1b8  main -> main
   ↑ two hashes and an arrow means it worked.

Looking around

git log --oneline -10      # recent commits          (q to quit)
git log --oneline --graph  # with branch structure
git diff                   # unstaged — what you've edited
git diff --staged          # staged — what you're about to commit
git show HEAD              # your last commit, in full
Stuck in a screenful of text you can't escape? git log and git diff open a pager. Scroll with arrows or space. Press q to quit.

Part 4When it breaks

The section you'll actually come back to. Nothing here is dangerous if you follow it as written. Search for whatever git just said to you.

Nothing matches that. Try undo, push, vim, key, or lost.
The universal escape hatch Almost nothing in git is permanently lost. git reflog lists every state your repo has been in, with hashes you can return to. And if you've truly tangled something: your files are on GitHub, so cloning fresh into a new folder and copying your uncommitted work across always works. Inelegant, reliable, no shame in it.

Part 5Cheat sheet

Keep this in a tab.

Daily

git status                    # what changed
git add -A                    # stage everything
git commit -m "Day NN: what"
git push                      # publish

make ship M="Day NN: what"    # all four + lint + tests

Looking around

git log --oneline -10         # q to quit
git diff                      # unstaged changes
git diff --staged             # what you're committing
git show HEAD                 # last commit in full

Undo

git restore <file>            # discard edits ← DESTRUCTIVE
git restore --staged <file>   # unstage, keep edits
git reset --soft HEAD~1       # undo last commit (if unpushed)
git stash / git stash pop     # shelve work / bring it back

When stuck

q                             # quit a pager
Esc :wq                       # quit vim, saving
git pull                      # push rejected? pull first
git reflog                    # every state you've been in
git rebase --abort            # back out of a messy pull

Setup, once

git remote -v                 # where does this push to
git config --global --list    # what have I configured
ssh -T git@github.com         # is my SSH key working
The one habit worth building now Run git status before every git add -A, and actually read it. Three seconds. It's how you catch the .env you forgot, the 400 MB file you didn't mean to include, and the twelve __pycache__ directories. Every experienced engineer does this reflexively — it's the highest-return git habit there is.
